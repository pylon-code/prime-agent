# Pylon upstream review ledger

This ledger records Prime upstream evidence and the decision taken for each overlapping Pylon feature. `.pylon/features.yaml` is the current machine-readable state; this file is the chronological review record.

## Entry template

- Date and upstream commit or release
- Prime issues, pull requests, releases, and source reviewed
- Affected feature keys from `.pylon/features.yaml`
- Decision: `adopt`, `hybridize`, `retain`, or `redesign`
- Reason and Pylon constraints
- Validation performed
- Follow-up or revisit trigger

## 2026-08-30 — attach-negotiated daemon session capability proof candidate

- Upstream baseline: `PrimeIntellect-ai/prime-agent@a903d4b6768f484bd6d459b7b0aa7dee38e461e2`; latest audited release remains `v0.8.1`.
- Reviewed current upstream daemon client/connection/protocol source and searched it for correlated prompt lifecycle, negotiated session capabilities, and post-attach proof. Upstream has none. The behavior is therefore not superseded by an upstream API.
- `negotiated-daemon-session-capabilities`: **retain** a narrow fork-boundary proof. At fork head `7238ac8`, `DaemonAgentConnection.supportsCorrelatedPromptLifecycle()` is server-offer evidence used before attach to advertise the client token. `DaemonAttachResult.client.capabilities` contains the daemon-established attach-side set, but no public accessor distinguishes that set from the hello offer. Pylon currently enables correlated mode from the offer, and Comet correctly refuses that inference.
- Candidate contract: add frozen root SDK token `negotiated_daemon_session_capabilities_v1` and public `supportsNegotiatedCapability(DaemonClientCapability)`. It is false before attach, while attach/reattach is pending, after replacement/socket close/dispose, and after failed or ambiguous attachment. It becomes true only after fixed-shape client identity/capability validation, snapshot identity and state staging, attachment-revision comparison, exact physical-transport generation comparison, shared-client ownership comparison, and the final local snapshot commit all succeed. Only a capability requested by this connection, echoed by the attach result, and offered by the same daemon transport can be proved.
- Generation and shared-client safety: every socket creation and clear advances a monotonic transport generation; direct `DaemonClient.close()` also clears the active socket and notifies close listeners exactly once. Attachment mutations sharing one `DaemonClient` are serialized because the supervisor stores client identity and capabilities globally per physical client. Starting any later shared-client attach invalidates all earlier proofs, including different-session peers, and only the latest committed attachment can remain proved. Session close/replacement, target invalidation during reattach, malformed proof, transport reset, dispose, and fail-closed snapshot reconciliation advance an invalidation revision that stale responses cannot cross.
- Disposal: public attach/reattach admission and the accessor fail closed from the first synchronous disposal step. An already-running owned-session recovery may perform one serialized, unproved internal reattach only to reach authoritative `complete_owned_session`; it cannot publish proof or restoration events. This preserves cleanup without reopening the public attachment API during disposal.
- Compatibility: keep `supportsCorrelatedPromptLifecycle()` as documented offer evidence because it constructs the pre-attach request. Strict consumers use only the new post-attach accessor. Offer-without-echo attaches successfully with proof false and without requiring a lifecycle snapshot. Stock 0.8.1 remains loadable but lacks the feature token/accessor. Replacement intentionally clears proof until a later attach result re-establishes it.
